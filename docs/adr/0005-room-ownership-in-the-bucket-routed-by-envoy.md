# Room ownership lives in the bucket, and Envoy resolves it in place of ingress-nginx

Redis did two jobs in the AWS demo: it held the Room Lock, and it carried the pub/sub for the two-phase coordinated Handover. Both exist because routing is a *hint* — ingress-nginx hashes `$uri` onto a ring that reshuffles on every scale event, so Sessions of one Room routinely reach a pod that does not own it, and the Handover protocol is what makes that survivable. **Remove the hint and both jobs disappear.** The AWS demo now keeps Room ownership in the same bucket that already holds Snapshots and Assets, and resolves it authoritatively at the proxy, so a live worker never receives a connection for a Room another live worker owns.

**Ownership is one object per Room**, `owners/{roomId}`, holding the owner's address. Every transition is the same primitive — a conditional PUT: `If-None-Match: *` to claim an absent record, `If-Match: <etag>` to reallocate a dead owner's, and `If-Match` again writing `owner: null` to vacate on drain. A `412` means someone else won; re-read and use their answer. There is **no lease and no delete**. No delete because release must be conditional or it is a split-brain — a worker draining could otherwise erase a record already reallocated to someone else — and conditional `DELETE`, while real on S3 since Nov 2024, returns `501 Not Implemented` on the LocalStack version this repo pins, so CAS-to-vacant is the one form that behaves identically locally and in production. No lease because ownership no longer needs one: liveness is answered by membership instead, and a per-Room lease renewed every 5s would cost roughly 25× more in PUTs than the read traffic it replaces.

**Membership is also in the bucket**, `members/{addr}`, written unconditionally by each worker on a 2s heartbeat and read by a `LIST` on a 2s poll; entries older than 8s are dead. This is a per-*worker* lease, not a per-Room one, so its cost is negligible. It replaces service discovery entirely: nothing queries the Kubernetes API, a GCE instance group, or DNS.

**Envoy replaces ingress-nginx** — it is not an added tier. A small stateless Node service, the **room-router**, exposes one pure function, `resolve(roomId, record, liveMembers) → addr`, as an `ext_authz` endpoint; Envoy calls it once per connection and routes the WebSocket to the named address through an `ORIGINAL_DST` cluster. Because `ext_authz` names an upstream for the non-affinity routes too, **Envoy performs no service discovery and holds exactly one cluster with no endpoint configuration**. On Cloud Run and in local Docker the same `resolve()` is wrapped in a proxy instead, splicing the sockets directly, because Cloud Run has no addressable instances and local development is better served by one container than by two. The full design, including per-runtime deployment for EKS, GKE, GCE, Cloud Run and Docker, is in [`../superpowers/specs/2026-08-19-bucket-registry-room-routing-design.md`](../superpowers/specs/2026-08-19-bucket-registry-room-routing-design.md).

**The coordinated Handover protocol is deleted.** Ownership now moves only when the previous owner is gone, which needs no cross-worker signalling: the draining worker deregisters, waits for routers to notice, persists the Snapshot, vacates the record, and closes its Sessions with `1013`. Clients reconnect and are resolved to a fresh owner that loads the Snapshot.

**Status:** accepted and implemented for the AWS demo, verified on `local-cluster`. Across a 2→3→4→3→2 scale cycle with 24 active Rooms, the drill measured **26 Room moves and 26 client disruptions before, 0 and 0 after**; a worker force-killed without draining had all 7 of its Rooms reclaimed with none left stale. EKS, GKE, GCE and Cloud Run remain to be deployed.

## Backend comparison: bucket vs Redis, measured

The record has to live somewhere, and that is a separable decision from routing resolving it. Both backends were built behind one interface and run on the same cluster, with the same drill and the same single-router configuration.

| | S3 (bucket) | Redis |
|---|---|---|
| Rooms moved, 2→3→4→3→2, 24 Rooms | **0** | **0** |
| Sessions disrupted | **0** | **0** |
| Failed connects | 0/120 | 0/120 |
| `resolve()` mean, isolated | **11.6ms** | **0.55ms** |
| `resolve()` distribution | 50/120 under 5ms | 126/126 under 5ms |
| Connect p50, end to end | 43–50ms | 36–51ms |

**The measured win is identical.** Both reach 0 Room moves and 0 disruptions, because that comes from routing resolving an authoritative record — not from which store holds it. Anyone reading this decision as "the bucket is what fixed scaling" has the causation wrong.

**Redis is ~21× faster at the thing it does, and it barely shows.** The isolated resolve is 0.55ms against 11.6ms, which is a real and repeatable difference. But a resolve is only about a quarter of connect cost; the rest is the WebSocket handshake, Envoy, and `TLSocketRoom` setup, so end-to-end connect latency is inside run-to-run noise on this hardware. The latency argument for Redis is true and mostly irrelevant.

**What actually separates them is cost and failure mode.** Redis is roughly 10–20× cheaper at 1,000 Rooms — a flat ~$0.016/hr against ~$0.29/hr of S3 requests, dominated by per-Room ownership reads. Against that, the bucket keeps liveness and the ability to persist on a single channel: a worker that cannot write Snapshots also cannot heartbeat, so it is evicted rather than left accumulating edits it can never save. Redis splits those, which is why the **persistence health check** exists — three consecutive failed Snapshot writes and the worker vacates its Rooms and fails its liveness probe. That tests the capability directly instead of inferring it, and is arguably the better mechanism regardless of backend.

Both ship. `registry.backend` selects one; the bucket is the default because "S3 and nothing else" is the simpler story, and the health check makes Redis a safe choice for anyone who wants the cost back.

## Alternatives considered

**A lease on the Room record**, mirroring the Redis lock directly — `{owner, expiresAt}` renewed by conditional PUT every 5s. Rejected on cost and redundancy: at 1,000 concurrent Rooms that is 200 PUT/s (~$3.60/hr) against ~$0.15/hr for the read-based scheme, and once membership carries liveness the lease answers a question already answered.

**A tighter 2s / 6s membership TTL.** Rejected as a false economy. `MEMBER_TTL` is a false-positive threshold as much as a detection latency: the expensive case is not a dead worker lingering in the live set but a *live* one evicted from it, whose Rooms are then reallocated while it still holds Sessions. Three missed beats leaves a worker one 2–3 second event-loop stall — a large Snapshot serialisation, a bucket latency blip — away from that. Four beats still reclaims inside ten seconds, which is what the "kill a worker" drill needs to read as recovery rather than a hang, and the extra cost of moving the heartbeat from 5s to 2s is about $0.05/hr at ten workers, so cost decided nothing here. Clean drains are unaffected at any setting: a draining worker deletes its record rather than waiting the TTL out.

**Having the router ping workers, rather than workers heartbeating to the bucket.** It detects failure faster, and the obvious objection — `N workers × M routers` requests per interval against `O(N)` — is the weak one, since those pings are free intra-cluster HTTP while the heartbeat is billed S3 PUTs. Rejected because it measures the wrong thing. A worker is entitled to own a Room because it can persist that Room's Snapshot, and the heartbeat is a PUT to the same bucket along the same path as that write, so liveness and the capability it authorises are a single signal with a single failure domain. A ping measures reachability from the router instead, splitting that in two: a healthy worker the router cannot reach is evicted and its Rooms reallocated while it is still serving Sessions and still able to write, and a worker partitioned from the bucket passes every ping while silently losing every edit. It also answers the wrong question, since a ping cannot say which workers *exist* — the roster is what `members/` is primarily for, and without a TTL nothing reaps a crashed worker's record. Finally it would break the worker's own membership self-check, which works only because both sides read the same signal; under pings the verdict lives only in the router and would have to be signalled back, which is the cross-node channel this decision deletes. Reachability is still used, but only as a routing preference: a router that cannot dial a worker stops sending it new connections and leaves its ownership records alone, because refusing to route is recoverable and reallocating ownership is not.

**`STRICT_DNS` for membership** — a headless Service, Docker's embedded DNS, or Cloud Map. It works; a compose service scaled 3 → 5 → 2 was verified to resolve to exactly 3, 5 and 2 A records, tracked live. Rejected because DNS responses truncate at 512 bytes over UDP, capping a name at roughly 25–30 records; because DNS carries an address and no metadata, so there is no room count for load-aware allocation and no way to signal draining; and because **a GCE managed instance group publishes no group-level A record at all**, which would have left that target needing Service Directory, a Terraform-rendered static list, or a file-EDS agent — three answers, one of them not dynamic.

**An xDS control plane.** Fixes truncation and metadata but not the underlying problem: something must still *discover* endpoints, meaning a Kubernetes informer on one target and a GCE API client on another — precisely the runtime-specific code this decision removes. It also adds a gRPC control plane with its own availability story.

**Keeping ingress-nginx and putting affinity in the app.** Possible, but nginx can only hash a path; it cannot ask which worker owns a Room. Retaining it would mean routing stays a hint and the Handover protocol stays with it, which is most of the complexity this decision removes.

## Consequences

**This supersedes [`0002-nginx-ingress-on-eks-for-room-affinity.md`](0002-nginx-ingress-on-eks-for-room-affinity.md)** in full. That record chose a self-managed ingress controller because ALB and NLB cannot hash on the request path; the reasoning is moot once affinity comes from a record rather than a hash. Its closing note on ElastiCache cluster mode is void — there is no ElastiCache.

**It partly invalidates [`0004-room-affinity-per-deployment-target.md`](0004-room-affinity-per-deployment-target.md).** That record's thesis is that Room Affinity is a property of the deployment target, answered separately by each. Under this design it is a property of the *application*, and any target that can route to an instance address can provide it — including Cloud Run, which 0004 pins to a single instance. The cost there is real but bounded: each worker becomes its own single-instance Cloud Run service, so scaling means deploying more services rather than raising a replica count.

**It weakens [`0001-duplicate-per-cloud-demos.md`](0001-duplicate-per-cloud-demos.md).** That record asks that the storage module stay the *only* intentional difference between demos, and names a second diverging file as the signal to revisit. `roomManager.ts` is now that file, and the routing tier diverges with it. The AWS demo has stopped being "the GCP demo with `s3Storage.ts` swapped in". This is accepted while AWS leads; porting the design to GCP is the point at which 0001 should be reopened rather than quietly ignored.

**[`CONTEXT.md`](../../CONTEXT.md) needs amending, and it will no longer describe both demos identically.** *Room Lock* is defined as "held for a fixed lease and renewed while owned", which is now false for AWS. *Room Affinity* is described as a hint that reshuffles on scale, and the example dialogue turns on that — "affinity is a hint, not a guarantee". That exchange is now correct for GCP and wrong for AWS, so the vocabulary must say which demo it is describing.

**`local-cluster` keeps ingress-nginx, and the AWS demo stops going through it.** nginx cannot leave that cluster — the GCP demo still hashes `$uri` on it for Room Affinity, and Grafana is served through it at `grafana.localhost` — so "remove nginx locally" is not available. What is available, and what this decision takes, is removing AWS traffic from it: a second k3d port maps `8081` straight to Envoy, and the AWS chart's `Ingress` is **deleted rather than re-annotated**. Fronting Envoy with a de-hashed nginx would have kept the `aws.localhost:8080` URL, at the price of making the local cluster the one place in the repo where Envoy genuinely is an added tier — demonstrating the opposite of this record's first claim. `verify-aws.sh` moves to `localhost:8081`, and the dashboard's 5xx panel gains an `envoy_http_downstream_rq_xx` series for AWS beside the existing nginx one for GCP, rather than silently omitting AWS.

**In proxy mode, this repo's code sits on the data path.** Every byte of every Session crosses the router on Cloud Run and in Docker. That is not true under Envoy, and not true of ingress-nginx today — nginx proxies, but it is not code this repo maintains. It is the price of the two targets where a proxy tier cannot or should not exist, and it makes the router's throughput a number worth measuring rather than assuming.

**Ownership is still check-then-write, not mutual exclusion.** The window between reading "I own this Room" and a Snapshot PUT landing is milliseconds, but non-zero. The Redis design had exactly the same window; conditional writes did not close it, and this record should not be read as claiming they did.

**Scaling up now disturbs nothing.** Existing Rooms keep their owner and only new Rooms land on new workers, where the hash ring previously dragged roughly a third of Rooms across pods on a 2→3 scale event. The `tldraw_handover_*` metrics and the local-cluster dashboard panels built on them become reclaim rate, reclaim duration and live member count; the drill becomes "kill a worker and watch its Rooms get reclaimed" rather than "scale up and hope a Room rehashes".
