# Room Affinity is solved per deployment target: nginx on Compute Engine, and not at all on Cloud Run

Room Affinity must be a function of the `roomId`. The GKE target gets it from ingress-nginx's `upstream-hash-by: "$uri"`, where `$uri` is `/api/connect/<roomId>` — a hash input the client cannot fail to send. **Google Cloud Load Balancing cannot reproduce this.** Its session affinity options are `CLIENT_IP`, `GENERATED_COOKIE`, `HTTP_COOKIE`, `HEADER_FIELD` and `STRONG_COOKIE_AFFINITY`: a header or a cookie, never the request path. So each new target had to answer the question separately.

**Compute Engine runs its own nginx tier.** A managed instance group of Container-Optimized OS VMs running stock nginx sits between the load balancer and a fixed set of app VMs, hashing `$uri` exactly as ingress-nginx does. This is mechanically identical to the GKE target, needs no client change, and imposes no same-origin constraint. The load balancer consequently has no session affinity configured at all — every nginx VM hashes identically, so which one a request reaches is irrelevant.

**Cloud Run cannot have it, so that target is pinned to one instance.** Cloud Run's session affinity is keyed on the client and documented as best-effort, there is no path-based hashing, and — decisively — Cloud Run exposes no per-instance addressing, so the nginx approach is unavailable: nginx would have exactly one upstream, the `run.app` URL, and Cloud Run would re-scatter behind it. Above one instance, client-keyed affinity does not degrade gracefully; it livelocks. A client reconnecting after a Handover is sent by its own cookie back to the instance that just gave the Room away, which requests it back, evicting the other client, and so on at roughly one Handover per second with a full GCS round trip each time. Disabling affinity only randomises it. `max_instances` therefore defaults to `1`.

## Alternatives considered

**`HTTP_COOKIE` + `RING_HASH` on the load balancer**, with the client setting a `tldraw_room` cookie carrying the `roomId`. Google's load balancer does hash a named client-supplied cookie, so this is a real ring hash on the `roomId` and it keeps the app tier autoscalable. Rejected because it moves Room Affinity from an unconditional server-side property to a conditional client-side one, and one client that omits the cookie is enough to livelock a Room. It also forces the client to be served **same-origin** with `/api/*`: cross-origin, a `SameSite=Lax` cookie is not sent on the WebSocket handshake at all, and a `SameSite=None` one is a third-party cookie subject to browser restrictions — so it would pass a manual test and silently degrade to the Cloud Run failure mode for a fraction of real users. It would also require changing the client and the k6 script, and any benchmark run without the cookie would measure a livelock rather than the system.

**`HEADER_FIELD` on `Sec-WebSocket-Protocol`**, carrying the `roomId` as a subprotocol. Cookie-free and origin-agnostic, which is genuinely nicer, but it requires implementing the client socket adapter by hand rather than using `useSync`'s `uri` option, and we could not confirm that the load balancer will hash on that header. Noted as the escape hatch if same-origin serving ever becomes impossible.

**A discovery sidecar for the Compute Engine app tier.** Consistent hashing in OSS nginx needs a static upstream list, and a regional MIG assigns addresses at create time, so an autoscaling app tier would need a component that polls the MIG, rewrites `nginx.conf` and reloads. Rejected as the most moving parts of any option and the piece most likely to be subtly wrong; the app tier is a fixed set of explicit instances instead.

## Consequences

The Compute Engine app tier has **no autohealing and no autoscaling** — resizing is editing a variable and re-applying. For this workload that is a smaller loss than it appears: every membership change reshuffles the hash ring and costs a Handover per moved Room, so it should be deliberate. CPU, the signal the GKE target's HPA uses, is the wrong signal here anyway, since idle Sessions cost almost no CPU and connection limits bind first.

The Cloud Run target is a **deliberate anti-example**, and it is the more valuable of the two for it. It demonstrates that the Room Lock alone is sufficient for correctness — no lost edits, no two owners, no stale Snapshot overwriting a newer one — while showing that Room Affinity being "only economic" does not make it safe to skip, because the price of getting the axis wrong is unbounded rather than merely higher. Its README leads with the mechanism and the metrics to graph.

This confirms ADR 0002's reasoning from the other side. That record predicted that an ALB-based AWS variant would make Handover the steady state; Cloud Run is that variant, and the observed behaviour is worse than "steady state" — it does not converge at all.
